P1SYS-01System & hardwareDefect / mismatch

Before reinstall: Disko targets a different NVMe drive

Trigger: Before any destructive install or TPM enrollment

This is an installer/recovery hazard; ordinary rebuilds do not repartition disks. Both machines inherit disko.devices.disk.vdb.device = /dev/nvme0n1. On the running 2025 machine, the EFI partition is /dev/nvme1n1p1 and the installed LUKS partition is nvme1n1p2. A second 953.9 GiB device occupies nvme0n1. The README's format and TPM-enrollment examples therefore identify a different device from the installed system at audit time.

Evidence, recommendation & verification ↗
Evidence classification Confirmed configuration / documentation defect
Confidence High

Why it matters

Reusing the documented installation procedure could erase the wrong drive. Running the TPM example can target the wrong partition or fail. Ordinary nixos-rebuild does not repartition the disk; this is an installer/recovery hazard. Current root and boot declarations mount by /dev/mapper/crypted and /dev/disk/by-partlabel/ESP, not by this installer device string. The broken standalone Disko example may fail before touching disks; the wrong-drive risk becomes reachable when that separate recipe defect is fixed or bypassed.

Recommendation

Move each machine's installation device identity into its machine module using a verified /dev/disk/by-id path, retaining the reusable partition layout in x86_64.nix. Rewrite enrollment/recovery instructions to resolve the installed LUKS backing device rather than assume a numeric NVMe order. Require a human-readable model/size/serial verification before any destructive format in the documented procedure.

What was checked / how to verify a change

Compare lsblk/findmnt and stable by-id links on both physical hosts. Evaluate the resulting disko device paths and inspect generated scripts without executing them. No partitioning or enrollment operation was run in this review. Changing the declaration does not migrate data; retain current labels until a separately planned reinstall.

P2AI-001Herdr & AIDefect / mismatch

Shell startup evaluates unquoted Slack token text as code

slack-stealth-tokens accepts printable characters such as $, parentheses, semicolons and spaces while scanning raw LevelDB bytes, then emits unquoted export assignments. Shell startup passes those assignments to eval. A synthetic token containing a harmless command substitution executed that substitution in the audit fixture.

Evidence, recommendation & verification ↗
Evidence classification confirmed defect
Confidence high

Why it matters

Malformed or attacker-controlled matching content in Slack local storage can become shell code when a new interactive shell starts. This is a proven parsing failure, not evidence that local storage has been compromised.

Recommendation

Prefer JSON output and data-only variable assignment. If preserving shell output, validate the entire token format and apply shlex.quote to values in both export and envrc output. Keep the helper's stdout limited to assignments and avoid printing token fragments on errors.
